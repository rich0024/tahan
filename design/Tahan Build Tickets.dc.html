Tahan · build tickets · milestones 1–4

Getting to v1

Thirty-two tickets that take Tahan from an empty repository to a private feed your family is actually using. They are written to be handed to a coding agent one at a time, in order: each names its own definition of done, and none of them requires a decision that hasn't already been made in the design or the backend spec.

Read first, and keep open: Tahan Flutter Handoff (theme values, both painter specs, screen inventory) and Tahan Backend Spec (collections, rules, deletion, build order). Tickets reference them rather than repeating them.

The prototype is the visual truth. When a ticket says "matches the prototype", it means Tahan.dc.html — open the relevant screen and compare rather than guessing.

How to run these with an agent

  • One ticket per session, in order. Paste the ticket, the two reference documents, and nothing else.
  • Every ticket ends with a build that runs on a real device. If it doesn't run, it isn't done — don't stack the next one on top.
  • Commit per ticket, message T1.4 avatar painter. When a ticket goes wrong you want one thing to revert.
  • Tickets marked ◆ are the ones worth reviewing carefully yourself. They are load-bearing, and a plausible-looking wrong answer costs a week.

Packages: firebase_core, firebase_auth, cloud_firestore, firebase_storage, firebase_messaging, cloud_functions, google_fonts (dev only — vendor for release), image or flutter_image_compress, connectivity_plus, shared_preferences, go_router. Nothing else without a reason — every dependency is a thing that breaks at the next Flutter upgrade.

Milestone 1 · A face

Auth, a user document, and the avatar painter with its editor. No village, no feed. Ends with you looking at your own drawn face on your own phone.

T1.1Project scaffold and Firebase wiring

Create the Flutter project, add the packages above, register iOS and Android apps, and get firebase_core initialising on both. Set up the Firebase emulator suite for local work — you will use it for every backend ticket.

Done when a debug build runs on a real iPhone and a real Android device and prints a successful Firebase init.

T1.2Theme and type

Build ScenePalette, the nine palettes from §1.2 of the handoff, the OKLCH ramp generator, and villageTheme(palette). Load Caprasimo and Figtree. Register the VillageScene theme extension.

Done when a throwaway screen shows headings in Caprasimo, body in Figtree, and swapping the palette constant retints buttons, cards and background. Watch for ramp steps generated in RGB instead of OKLCH — they go muddy, and warmth is the point.

T1.3◆ Paint primitives and the path parser

Implement the six primitives (rect, circle, ellipse, filled path, stroked path, sky gradient) as a small sealed model, plus a parser for absolute M L Q C Z only. Both painters are built on this, so it is worth twenty extra minutes of care.

Done when unit tests cover each command and the parser throws on relative commands and arcs rather than silently mis-drawing. Watch for an agent "helpfully" adding h/v/A support — reject it; the geometry scaler assumes every number is an absolute coordinate pair.

T1.4◆ AvatarPainter

Port the avatar geometry from the prototype: the 78-unit authoring box, the kit colours from §3 of the handoff, eight hairstyles, four facial-hair options, four glasses, five clothes. Painter takes an AvatarSpec of six ints and a background palette.

Done when a debug grid of 24 random specs renders at 26, 44 and 96 px and every combination is legible with no clipped hair or floating glasses. Watch for features drawn in the wrong z-order at small sizes.

T1.5Avatar widget and picture cache

Wrap the painter in an Avatar(spec, size) widget that caches by spec+size as a ui.Picture, and carries a Semantics label with the person's name.

Done when a list of 200 avatars scrolls at 60fps in profile mode.

T1.6Sign in

Phone or email link — pick one and only one for v1. Create /users/{uid} on first sign-in with a randomised avatar spec and an empty display name.

Done when signing in twice on the same device reuses the same user document, and signing out returns to the start.

T1.7Avatar editor screen

The Me-tab editor from the prototype: the large avatar drawn on a scene sky, swatch rows for skin, hair colour and clothes, segmented rows for hairstyle, glasses and facial hair, and "Surprise me". Writes the six ints to the user document.

Done when changes render instantly, survive a force-quit, and every control is at least 56 px tall.

T1.8Companion avatar

The optional second avatar — dog, cat or baby — with a coat index. Belongs to the user, not a village.

Done when a companion can be added, edited and removed, and the editor tabs between it and your own face.

Milestone 2 · A room

The nine scenes, the drift, the window, and the retint. Still no data — this milestone is entirely drawing, and it is what makes Tahan feel like Tahan.

T2.1Scene data

Port all nine scenes' layer lists and sky gradients into paint/scenes/, one file each, using the primitives from T1.3. Straight transcription from the prototype; no reinterpretation.

Done when each scene's layer count and colours match the prototype exactly.

T2.2◆ ScenePainter

Paint a scene from its layer list into an arbitrary rect: authored at 402×216, scaled uniformly on width, anchored top, bottom gradient stop stretched so the sky can run the full height of the app. Parse and cache paths once at startup.

Done when all nine render correctly at header height (216) and at full screen height, on a short phone and a tall one, with no stretched geometry.

T2.3Time-of-day wash

One low-alpha overlay tinted by the local clock: morning, afternoon, evening, night. Recompute on app resume, not just cold start.

Done when changing the device clock across the four bands visibly changes the wash after a resume.

T2.4◆ Ambient drift

Seven effects — fireflies, leaves, breeze, dust, rain, snow, petals — 18–26 shapes on a single repeating controller, with deterministic per-index phase from a hash of index and scene key.

Done when drift pauses on background and off-screen, and draws zero particles (not slowed ones) when MediaQuery.disableAnimationsOf is true or the app's Ambient motion setting is off. Watch for Random() — the pattern must be stable across rebuilds.

T2.5Glass, sill and parallax

Diagonal sheen, edge vignette, warm ledge, and the backdrop translating at one sixth of scroll offset, clamped so the sky never lifts off the top. All inside a RepaintBoundary.

Done when scrolling a long dummy list stays at 60fps on the oldest device you intend to support.

T2.6Scene switching retints the app

Changing the scene swaps the palette for the whole app over 420 ms with an ease-out curve, chrome included.

Done when cycling all nine scenes shows no flash of the old accent and no unthemed widget.

Milestone 3 · A village

The privacy boundary, made real. Rules and the invite flow come before any content, because retrofitting them is the one mistake you cannot cheaply undo.

T3.1◆ Firestore, rules and rule tests

Create the collections from the backend spec, write firestore.rules and storage.rules as specified, and enable offline persistence with an unlimited cache.

Done when the emulator rules test suite proves a non-member cannot read a village's posts, a member cannot appoint an admin, and a member cannot edit another member's post. Those three tests are the product's whole promise.

T3.2Create a village

Name, scene picker, creator becomes admin, member document written with a copy of their display name and avatar.

Done when the new village's scene immediately themes the app.

T3.3Invite mint and redeem functions

Two callable functions. Mint writes /invites/{token} with an expiry; redeem validates, writes the member document, marks the token used. Clients never write either collection.

Done when a token works exactly once, an expired token fails cleanly, and the share sheet is the platform's own.

T3.4The invitation screen

The pre-join deep-link target from the prototype: the village's own scene, the host's name, who is inside, the two reassurance lines, "Join the village". Renders before the user has an account.

Done when a cold-start deep link lands here, and joining goes straight into the feed.

T3.5Members and admin

The members list, admin-gated: appoint and remove admins, remove members. The creator is admin and cannot be the last admin removed.

Done when a non-admin sees the list but no controls, enforced in rules as well as UI.

T3.6Village switcher

The header avatar opens the switcher: villages as lit doors, each in its own scene, plus the scene picker for the current village.

Done when switching villages retints the app and the feed reloads from cache first.

T3.7◆ leaveVillage function

Implement the deletion table from §6 of the backend spec as one callable function, with the keep-or-leave-behind choice for recipes stubbed until milestone 5. Removal by an admin calls the same function.

Done when an emulator test seeds a member with posts, photos, notes and reactions, calls the function, and asserts every one of them is gone — including the Storage objects.

Milestone 4 · The feed — this is v1

Updates, photos, four reactions, notes and the daily status line. When this milestone is done, the family goes on it. Nothing below is optional; nothing above milestone 4 ships with it.

T4.1App shell

The four-tab bar — Home · Village · + · Me — drawn by the app rather than the platform, with the accent following the scene. The + opens a native modal sheet.

Done when the bar looks identical on both platforms and every target is at least 56 px.

T4.2Post model and repository

The post document, a paginated feed query ordered by createdAt, and a repository that serves cache first. One card widget with a type variant — not five widgets.

Done when the feed renders from disk in airplane mode with no spinner.

T4.3Compose an update

Text update posting into the feed, in the composer sheet from the prototype.

Done when a post written offline appears immediately in a "sending" state and settles when signal returns.

T4.4◆ Photos and the upload outbox

Client-side resize to a 1600px long edge plus a 400px thumbnail, upload to /villages/{vid}/{postId}/, and a persistent outbox of pending uploads that retries on connectivity. Never upload the camera original.

Done when three photos queued in airplane mode all arrive after a force-quit and a reconnect.

T4.5Reactions

Four and only four — heart, thanks-hands, smile, star. One document per user plus a transactional count on the post. No picker, no sixth option.

Done when two devices reacting simultaneously both land, and changing your reaction moves the count rather than adding one.

T4.6Notes

One threaded notes widget used on every content type, in the app's voice ("3 notes", never "comments"). Author or admin can delete.

Done when the same widget opens from a post and from a photo with no per-type branches in the UI.

T4.7The daily status line

The face row at the top of the feed, one line each, with a TTL policy on expiresAt. It never sends a notification.

Done when a status disappears on its own overnight without a cleanup job.

T4.8Actionable push

FCM plus the Firestore trigger for notes and thank-yous, with reply and thank actions on the notification itself. These are the only two senders in v1.

Done when replying from the lock screen posts a note without opening the app.

T4.9Day one

The two-member empty state from the prototype: the house carries it, three gentle prompts, and no invented activity anywhere.

Done when a brand-new village shows it and it does not look like an error.

T4.10◆ The 150% pass

Walk every v1 screen at 150% text: layouts go vertical, reaction rows collapse behind one button, targets stay at 56 px, nothing truncates. Never cap textScaler.

Done when a screenshot of every screen at 100% and 150% sits side by side and you would hand either to your grandmother.

T4.11Ship it to the family

TestFlight and an Android internal track, scheduled Firestore exports turned on, a billing alert set, and one real invitation sent to a real person.

Done when someone who did not build it posts something you did not ask them to post.

After v1

Do not start milestone 5 for two weeks. Watch what the family actually does — which of recipes, routines and events they ask for first should decide the order, and one of the three may turn out not to matter at all. The three undesigned screens (Who sees me?, the printed recipe card at real size, the moderation take-down view) are worth designing during that fortnight, while the feed earns its keep.
