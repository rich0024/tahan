What Tahan stores, and who can see it

Tahan is twelve people, private, photo-heavy and used on bad rural wifi. That combination decides almost everything below: there is no feed to rank, no discovery to index, and no scale problem — but there is a hard privacy boundary and a real offline requirement. This is the schema, the rules that enforce the boundary, what happens when someone leaves, and the order to build it in.

Companion documents: Tahan Flutter Handoff (theme, painters, screens) and Tahan.dc.html (the working prototype). This one covers only what lives on a server.

1 · The recommendation

Firebase — Firestore, Storage, Auth, Cloud Functions, FCM. Not because it is fashionable, but because it is the only option that gives you the offline behaviour for free: Firestore's local persistence means the feed opens instantly with last-known content, writes queue on disk and replay when signal returns, and you never write a sync layer. On a Flutter app for twelve people, that is most of the backend work already done.

The honest alternative is Supabase — nicer to reason about, real SQL, row-level security that reads like English. Its offline story in Flutter is still yours to build. Pick it only if you already know Postgres well and would rather own the sync than own Firestore's query limits.

1.1 What it costs at family scale

One village of twelve, opening the app a few times a day, sits inside Firebase's free tier with room to spare — the bill only starts when photo storage grows. Budget for storage and egress, not reads. Rough shape: a few hundred photos a month at 1600px is single-digit gigabytes a year. Set a billing alert at a number that would surprise you and forget about it.

The one thing to get right up front: a village is the permission boundary, so every document that isn't a user's own must live under /villages/{villageId}/. Rules can then be written once against membership instead of per-collection. Retrofitting this later means rewriting every query in the app.

2.1 Notes on the shape

  • Recipes are the exception to the village-owned rule, and deliberately so — the design says a recipe is yours and gets lent to a village. sharedWith is the whole sharing mechanism; a village post of type recipe only points at it.
  • Reaction counts are denormalised onto the post so the feed is one query. Write the count and the per-user doc in the same transaction; at twelve people contention is not a concern.
  • Statuses expire — use a Firestore TTL policy on expiresAt rather than a cleanup job.
  • No users collection reads in the feed. Name and avatar are copied into the member doc and read once per village session; a function refreshes them when a user edits their avatar.

3 · Avatars are data, not files

The six integers in avatar are the entire representation — no uploads, no crops, no image hosting, no moderation surface, and nothing to migrate. Store them as a map, validate the ranges in rules (skin/hairColor/top 0–4, hair 0–7, glasses/face 0–3), and let the painter do the rest. This is the cheapest good decision in the whole product; don't let a "just add photo avatars" ticket in later without arguing about it.

4 · The village boundary

Every rule reduces to one question: are you a member of this village, and are you an admin? Write those two helpers once.

rules_version = '2'; service cloud.firestore { match /databases/{db}/documents { function member(vid) { return exists(/databases/$(db)/documents/villages/$(vid)/members/$(request.auth.uid)); } function admin(vid) { return get(/databases/$(db)/documents/villages/$(vid)/members/$(request.auth.uid)) .data.role == 'admin'; } function mine(uid) { return request.auth.uid == uid; } match /users/{uid} { allow read, write: if mine(uid); match /recipes/{id} { allow read: if mine(uid) || resource.data.sharedWith.hasAny(memberVillages()); allow write: if mine(uid); // only the author ever edits a recipe } } match /villages/{vid} { allow read: if member(vid); allow update: if admin(vid); // name, scene allow delete: if false; // villages are archived, never deleted match /members/{uid} { allow read: if member(vid); allow create: if false; // joining goes through redeemInvite() allow delete: if admin(vid) || mine(uid); // remove, or leave allow update: if admin(vid); // appoint / demote } match /posts/{pid} { allow read: if member(vid); allow create: if member(vid) && request.resource.data.authorId == request.auth.uid; allow update: if mine(resource.data.authorId) || onlyChanges(['reactionCounts','noteCount']); allow delete: if mine(resource.data.authorId) || admin(vid); // moderation match /reactions/{uid} { allow read: if member(vid); allow write: if member(vid) && mine(uid); } match /notes/{nid} { allow read: if member(vid); allow create: if member(vid); allow delete: if mine(resource.data.authorId) || admin(vid); } } match /events/{eid}/bring/{rid} { allow read: if member(vid); // anyone may claim an OPEN row, or release their own — nobody takes another's allow update: if member(vid) && ((resource.data.claimedBy == null && request.resource.data.claimedBy == request.auth.uid) || (resource.data.claimedBy == request.auth.uid && request.resource.data.claimedBy == null)); } } match /invites/{token} { allow get: if true; // a newcomer must see who's inside allow write: if false; // minted and redeemed by functions only } } }

Two notes. member() costs one document read per rule evaluation — fine here, and worth it for rules you can actually read. And the invite document is the only thing outside the boundary: it exposes the village name, the member count and the host's name to whoever holds the link, which is exactly what the invitation screen shows and nothing more.

5 · Offline, and why the boards are documents

Turn on Firestore persistence with an unlimited cache size and the read path is solved: the feed renders from disk before the network answers, and writes queue locally. What you must design around is the conflict model — Firestore merges at the field level and last write wins.

That is why a bring-list row is its own document rather than an element in an array on the event. Two people claiming two different rows from two kitchens with no signal is the normal case; if rows were an array, one of them would silently lose their claim on reconnect. Same reasoning for reactions (one doc per user), notes and check-ins. Anywhere two people can act at once, give each person their own document.

  • Claiming an already-claimed row is the one race the rules reject outright — show "Nina got there first" rather than a generic error.
  • Photos do not queue in Firestore. Keep an outbox table of pending uploads with the local file path, retry on connectivity, and show the post in the feed with a soft "sending" state.
  • Cache the last ~200 feed items and their thumbnails on disk deliberately; don't rely on the OS image cache.

6 · Leaving, removing, deleting

The design promise is specific and must be implemented literally: your updates and photos leave with you; recipes are yours to keep or leave behind. Do it in one callable function, never client-side.

WhatOn leaving / being removed
Posts you authoredDeleted, with their notes and reactions subcollections.
Photos you uploadedStorage objects deleted — including any inside albums.
Notes you left on others' postsDeleted. Parent noteCount decremented.
Reactions you gaveDeleted, counts decremented.
RecipesYour choice, asked in the leave sheet: keep removes the village from sharedWith; leave behind copies the recipe to the village under your name and keeps yours.
Routines you ownedDeleted with their check-ins. Routines others check for you are reassigned to the host.
Event rows you claimedReleased back to open, so the host sees the gap reappear.
Your membershipDeleted; memberCount decremented; village id removed from your user doc.

Removal by an admin runs the same function with keepRecipes: true. Account deletion runs it for every village, then deletes /users/{uid}. Neither is undoable, and both should say so plainly before they run.

Moderation take-down (an admin deleting someone else's post) is a different act and should leave a trace: write /villages/{vid}/moderation/{id} with the actor, the author, the time and the post type, and tell the author. The screen for it is still to be designed.

7 · Photos

Storage path /villages/{vid}/{postId}/{uuid}.jpg, mirroring the Firestore boundary so the same membership rule protects both. Resize on the client before upload — a 1600px long edge for viewing and a 400px thumbnail — and never upload the camera original; it saves the user's data plan and most of your storage bill. Signed URLs are unnecessary: rules cover it.

8 · The three notifications

Push is rare by design, so there are only three senders — resist adding a fourth.

9 · Build order

You have a real first village — your family — which means you can cut hard and still ship something worth using. Each milestone below is a thing they can do, not a layer.

#MilestoneIncludes
1A faceAuth, user doc, the avatar painter and editor. No village yet. Ship it to yourself.
2A roomThe scene painter, the nine palettes, theme switching. Still no data.
3A villageCreate, invite link, redeem, members list, admin roles.
4The feedUpdates, photos, the four reactions, notes, the daily status line. This is v1. Put the family on it here.
5The cookbookRecipes, sharing, printing the card.
6Routines & listsSelf-reported check-ins, streaks, visibility.
7EventsBoth boards, RSVP, the pinned card.
8The letterSunday digest, albums, milestones.

Milestones 1 and 2 are the painters, and they come before any screen on purpose — they are the only genuinely novel code in the app, and everything after them is ordinary Flutter that an agent can produce quickly from the handoff document.

10 · Still open

  • Search. Nothing above supports it. At twelve people and a few hundred posts, client-side filtering over the cache is genuinely enough — decide that consciously rather than reaching for an index later.
  • Multi-village users. The schema supports it; the digest and the notification budget assume one. Decide what a person in four villages gets on a Sunday.
  • Export. "Your photos leave with you" implies a download. A function that zips a user's posts and photos is a day's work and worth doing before the first person leaves.
  • Backups. Turn on scheduled Firestore exports on day one. This is a family's photographs.
